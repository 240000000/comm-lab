# 通信原理交互实验室

一个在浏览器里跑的小实验室：把通信原理课上那几条公式变成能拖的图。不用装 MATLAB，不用配环境，打开网页就能看星座点怎么被噪声推散、卷积码怎么把打翻的比特纠回来。

在线地址：https://240000000.github.io/comm-lab/

本文件对应仓库 tag R8，仓库在 https://github.com/240000000/comm-lab 。想对着看代码，`git show R8` 能看到这一版的全部改动。

---

## 一、这个项目是干什么的

我在通信原理课上背了一学期的公式——QAM 星座图长什么样、误码率随信噪比怎么走、卷积码为什么能纠错——全是符号。考试换个信噪比，我就得从头推一遍，还推不对。真正的问题不是不会算，是看不见：星座点被噪声推离原位是什么样子、一帧比特里哪几位被打翻、译码器凭什么说这几位是错的，这些在纸上都没法画。

所以我把它们做成了网页上的三个实验台。拖一下信噪比滑块，十六个星座点立刻变成十六团云；翻两个比特，看译码器把它们全纠回来；翻四位，它纠不回来，页面就照实写「还有 3 位没纠回来」，不替我圆。

## 二、怎么用

1. 打开 https://240000000.github.io/comm-lab/ 。首页是四张卡片，现在能点的是前三张。
2. 点第一张「QAM 星座实验台」。左边是星座图，右边是控件。
3. 把右边的「信噪比 Es/N0」滑块从 20 dB 往左拖。20 dB 时 EVM 约 10%，点基本贴着理想位置；拖到 12 dB，每个点变成一小团；拖到 0 dB，整片都是琥珀色的散点，已经分不出原来那个点在哪。
4. 看下面三个读数：误码率、误符号率、误差向量幅度。每个数字后面都写着它是多少个符号、多少个比特算出来的——0 dB 时误码率是 2.86e-1，括号里写「错 22,916 个比特 / 共比对 80,000 个比特」。
5. 再往下是 0–20 dB 的误码率曲线，灰色虚线是公式算的理论值，实心点是这批样本实测的。
6. 回首页点第二张「卷积码与 Viterbi」。上面是一条 12 比特短序列的四行：原始、编码后、加噪后、译码后，琥珀色格子是接收端被打翻的、红色是译码后还错的。右边可以关掉噪声，也可以手动翻 2 位、翻一片 4 位，再切硬判决和软判决两套译码器；下面三条线是同一批信噪比下不编码、硬判决、软判决的误码率对照。
7. 回首页点第三张「OFDM 时频链路」。右边两个滑块：循环前缀长度（默认 16）和延时径的延时（默认 9）。延时不超过 CP 时，左边的时域图上紫色虚线只落在 CP 的浅色底里，下方「有 CP」的误符号率写「这次没出错」，「没有 CP」那边已经错了 254 个符号；把延时拖到 21，灰色提示变成「拖尾压进数据段 5 个采样」，两条误符号率一起往上走。最下面是 64 个子载波上的接收点，有 CP / 无 CP 并排。

## 三、现在做到哪一步

QAM 星座实验台已经能玩。阶数写死 16QAM，暂不支持切换，可调的是信噪比 0–20 dB，读数、点云、误码率曲线都在。

卷积码与 Viterbi 也能玩：约束长度 3、码率 1/2、生成多项式 7 和 5，硬判决与软判决是两套独立的译码器，12 比特短序列四行对照，外加 0–10 dB 三条线的对照曲线。

OFDM 时频链路也能玩，而且刻意只做了「循环前缀挡住什么」这一件事：64 个子载波、QPSK、一条主径加一条延时径，CP 长度 0–24 可拖。不做信道估计、不做均衡、不做频偏——这三样页面里都写明了没做。

任务模式还没开始。

版本 v0.6。测试 82 条，全部用 Node 自带的 test runner 跑，没有引入任何测试框架。

## 四、亮点

对我来说最有用的一点：它把「看不见」变成「看得见」，而且数字不肯含糊。

先说数字。每个读数都带分母，误码率不是孤零零一个 2.9e-2，而是「2,331 / 80,000」。样本不够的时候它不装懂——20 dB 那个点实测一个比特都没错，页面写的是「这次没出错，0 / 80,000」，曲线上画成空心圈，因为这一批样本能分辨的最小误码率就是 1/80,000，再低就看不见了，不是真的零。

同一个种子重跑，数字一模一样；界面上写着这次实际用的种子，也能自己填。

还有一处我特意留着没改。卷积码那页 0–2 dB 一段，硬判决的误码率比不编码还高。这不是 bug：码率 1/2 让每个信息比特只分到一半能量，硬判决又把幅度信息扔了，低信噪比就先付这笔账。图注里就这么写的。

## 五、AI 是怎么参与进来的

这个项目是我和 AI 一轮一轮做出来的，每轮结束把当轮对话原文存进仓库（`docs/dialogues/`），一个 commit、一个 tag。它不是我描述一遍需求、它一次生成的。挑几件具体的说。

第一轮我让它先别写代码，先给判据。它预测「还没有测试文件时 `npm test` 会失败」，实际跑出来是 0 个测试、退出码 0。它当场承认判据写错了，改成「测试数不少于 21 条、fail 为 0」才动手。

存档那件事我更在意。它写的对话存档被我抓出不是原话，四句的措辞和屏幕上差着。我要求：存档必须是复制粘贴的原话，拿不到就标「原文缺失」，不许重写；也不许 amend 旧提交，单开一个 fix 提交改回来，让「我发现自己没逐字」这件事留在历史里。从那轮起改成先写进存档、再从存档复制进回复。

还有一次它差点把占位符当原文收下。我说原文贴了，实际正文里只有一行模板占位。它没照抄，而是指出来「这不是原文」，让我重贴——这个判断是对的。

首页那句「能调 QAM 阶数」是它写的，可阶数其实写死 16。我在提交前逐句核对时抓到，要求改成只写现在真能做到的，功能等十一月再加。

图注压住横轴刻度、点云太糊看不清标签，都是我截图之后挑出来的，它改完我再截一遍确认。它想省事的地方我自己立规矩：某个信噪比下一条错都没有时，不许写 1e-5 糊弄，要么写「这次没出错，0/n」，要么直说样本不够；曲线上样本不够的地方画空心，不许硬连。

这些都是我抓着改的。它写得快，但「写得像真的」和「真的」是两回事，每一轮都得我自己去核。

## 六、关键技术

整个项目是纯前端：Vite + React + TypeScript，没有后端、没有数据库，运行时不调任何模型接口，也不需要任何密钥，静态托管在 GitHub Pages 上。算法全部自己写，一个通信库都没引——星座映射与格雷码、AWGN 加噪与最近距离判决、误码率理论曲线（erfc / Q 函数的数值拟合）、卷积码网格与编码、硬判决与软判决两套 Viterbi、自由距离搜索，都是 `src/core/` 下的纯函数，评委可以直接读。

随机数可复现。用 mulberry32 生成均匀分布，Box–Muller 转成高斯噪声；每次仿真用「种子 + 信噪比」派生出这一次真正用的种子，并显示在界面上，同一个种子、同一个信噪比，重跑出来的点和读数逐位相同。软判决和硬判决的差别也在这层：硬判决先把接收幅度按 0 门限切成比特，再比汉明距离，「收到 0.02」和「收到 0.49」都变成同一个 0，离门限多远这层信息就丢了；软判决不切，直接拿接收幅度到 ±1 理想点的平方距离当分支度量，越远的候选代价越高。同一批参数下（11 个信噪比点、每点 20,000 个比特、同一种子），4 dB 时硬判决错 203 个比特、软判决错 11 个。

码距不是抄来的。约束长度 3、生成多项式 7 和 5 这组码，自由距离 dfree = 5 是程序在网格上搜出来的，纠错能力 ⌊(5−1)/2⌋ = 2 位，页面上写明「一个约束窗口内」。性能上，QAM 那条 21 点 × 20,000 符号的曲线本机约 60 ms 扫完，卷积码 11 点 × 20,000 比特的三条线约 178 ms，单次 20,000 个符号的仿真约 5.1 ms，拖滑块不会卡。

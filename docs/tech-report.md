## 第一章 意图控制策略

这一章讲怎么控制一个会自己写代码的东西，以及控制失效时的五次具体事故。

先说控制手段本身。它由三条构成，三条都是踩过坑之后才定下来的。

第一条是每轮开工前先写"怎么算做完"，给用户看，用户同意了才动代码。R9 那轮的判据写了八条，用户逐条改过，其中一条当场被证明是错的（见 1.2），另外四条被改了措辞或补了前提。判据不是走形式：它决定了这一轮结束时我拿什么交差，也决定了用户拿什么否我。

第二条是每轮结束把对话原话落进 `docs/dialogues/`。用户侧逐字、AI 侧也逐字，写不出来的段落标"原文缺失"，不许补写。这条规则来自一次事故：R1 的存档是我凭对话回放写的，措辞与屏幕上显示的不一致，用户逐字核对后指出了 4 处；那一轮补了一个 `fix(docs)` 提交（`3be4d19`）改回原文，没有 amend、没有重打 R1 的 tag，让"我发现存档不逐字"这件事留在历史里。从那以后 AI 侧的正文改成"先写进存档、再从存档复制进回复"，两边不一致就是我的问题。

第三条是所有对外出现的数字都必须能回代码里现算。文档里的数不许从上一轮结论里抄，页面上的数不许和仿真脱钩。1.3 和 1.4 两节都是这条规矩的代价。

下面五节按发生顺序，每节只说三件事：怎么发现、机理是什么、最后改成什么。节末不写总结，因为总结容易被写成"这体现了严谨"，那不是事实。

### 1.1 延时取 8 和 16 会撞上零陷

R9 设计 OFDM 实验台时，第一版参数里有"延时 8"和"延时 16"，因为这两个数好记，也正好是 64 的约数。判据写完给用户看，用户当场否掉：64 个子载波、延时正好 8 的时候，有八个子载波上的两径反相抵消，接收点直接落到原点，QPSK 四点离原点一样远，判决成了平局，"有 CP 那一侧误码为零"这条会当场被打脸（`docs/dialogues/2026-10-26-session-02.md:935`）。用户的原话是"这不是代码写错，是参数撞上了零陷"。

机理不复杂。链路是

```
y[m] = x[m] + a·x[m-delay]
```

a 是延时径相对幅度（`src/core/ofdm.ts:109`）。换到频域，第 k 个子载波上的增益是

```
H[k] = 1 + a·e^(-j2πk·delay/64)
```

a = 1 时令 `k·delay/64 = 1/2`，H[k] 正好为零。delay = 8 时 k = 4、12、…、60 共八个点落进零陷；delay = 16 时是十六个。判决按象限取号（`src/core/ofdm.ts:41`），接收点落在原点，四个理想点离它一样远，取哪个都算错，而且"有 CP"与"无 CP"两侧的结果会变得难以解释——一侧看起来全对，另一侧看起来一半对，实际上是同一批子载波在同时出错。

这不是代码 bug，也不该靠改代码解决。实测更直接：把延时径幅度临时调到 0.9（接近等幅），delay 9 的"有 CP"一侧立刻掉到 1040 个错（存档 `:978`）。等幅才会完全抵消，0.9 已经够糟。

发现它的过程也值得记：不是读代码读出来的，是把页面上的延时滑块拖到 8 看了一眼——频域那 64 个点里有 8 个落在正中间、四簇点围着原点转，读数上"有 CP"一侧的 SER 从 0 跳到和"无 CP"差不多的水平。当时第一反应是判决写错了，回头检查 `decideQpsk`（`src/core/ofdm.ts:41`）才发现它没毛病：四个理想点离原点等距，取哪个都算错。**参数把一个正确的判决器逼成了必然出错**，这类问题只能靠"换一组参数再看一遍"暴露。

所以修法有两层：参数层把延时改成除不尽的数，结构层把幅度定死 0.5（`ECHO_AMPLITUDE`，`src/core/ofdm.ts:26`）。后一层是关键——只要幅度不是 1，`H[k]` 就不可能为零，零陷从"可能踩到"变成"踩不到"。`tests/ofdm.test.ts` 里没有直接断言"幅度不等于 1"，因为常量不是这样用的；真正锁住它的是"无多径 EVM 小于 1e-9"与"delay 9 有 CP 侧 0 错"这两条——谁把幅度改回 1，后者会立刻变红。

最后改成什么：延时径幅度定死 0.5，功率是主径的四分之一（`src/core/ofdm.ts:26`，`const ECHO_AMPLITUDE = 0.5`），保证任何一组参数下都不出现完全抵消；延时改用 5、9、21、33 这类与 64 除不尽的数，页面默认 9、超 CP 的演示用 21。开工前先跑了一遍 cpLen 固定 16、延时 1 到 33 的扫描，把有 CP 与无 CP 两条 SER 打出来挑默认值，扫描表在存档 `:985` 到 `:993`：delay 5 是有 CP 0 错、无 CP 107 错；9 是 0 对 254；12 是 0 对 346；16 是 0 对 381；17 是 0 对 457；21 是 111 对 511；25 是 271 对 511；33 是 431 对 531。这一步是用户要求的（存档 `:943`），理由是"别到最后才发现默认值正好卡在零陷上"。

0.5 这个值也是挑出来的。太小则无 CP 一侧坏得不够明显，演示不出"CP 有用"；太大则逼近零陷，两侧结果会变得难以解释。0.5 对应 3 dB 的功率差，正好在"看得出差别、又不会反过来"的区间里。

扫描本身也有口径：每个点 200 个符号、12,800 个 QPSK 符号，种子固定 20261027。200 个符号不算多，所以 0.1% 以下的差别看不出来——扫描只用来选默认值，不作为结论。页面上的数用同一批参数，读者可以自己对出来。

### 1.2 判据五写错了：循环前缀不是免疫

同一轮，验收判据的第五条原本写的是"延时超过 CP 时，无 CP 一侧误码明显上去，有 CP 一侧仍是零"。用户批准了其余七条，只对这条加了前提：延时必须与 64 除不尽。判据贴着这句话做完，实测结果却是：cpLen 16、delay 21 时，有 CP 侧错 111（8.67e-3），无 CP 侧错 511（3.99e-2），**两侧都在错**（存档 `:967`）。

原因在于 CP 的物理作用边界。它把多径拖尾挪进前缀里，能吸收的延时上限就是 cpLen 个采样。延时不超过 cpLen 时，拖尾整个落在前缀内，数据段干净，频域没有码间干扰；超过之后，拖尾压进数据段，误差从零变成非零。有 CP 一侧的优势只是"晚一点开始坏、坏得轻一点"，不是"不会坏"。这一条在超出 CP 之后没有任何机制能救——页面里没有均衡器，也不打算有。

用式子看更直白。接收端第 k 个子载波上的值是

```
Y[k] = H[k]·X[k] + I[k]
```

`H[k]` 是两径信道在该子载波上的复增益，`I[k]` 是前面符号的拖尾压进来的部分。CP 足够长时 `I[k] = 0`，只剩一个乘性系数，判决只看象限，乘性系数是几都不影响；CP 不够长时 `I[k] ≠ 0`，它是随机的，翻不翻象限全看运气。这也解释了为什么"超了 CP 之后错误率不会一路飙到 100%"——多数时候拖尾不至于把点推出象限。

改成什么：页面读数、判据表述、验收表全部改为"延时超 CP 后两侧都错、有 CP 侧更轻"；页面上还多了一个直接读数——`wave.intrudingSamples` 算出压进数据段的采样数，时域图右上角写"拖尾压进数据段 5 个采样"。测试 `tests/ofdm.test.ts` 里对应一条断言 delay 21 时两侧都有错、且无 CP 侧错得更多。这条更正同时写进了那一轮的对话存档，原始判据与更正后的说法并存，评委会看到改之前和改之后各是什么样。

页面底部还留了三张说明卡：CP 消的是码间干扰、不消频域衰落；这一页里没有噪声，所有误码都来自码间干扰；CP 的吸收范围就是 cpLen 个采样。这三句话都是为了防"CP 万能"这个误解，比任何一段总结都直接。

判据里其余几条都过了，而且都落成了测试：64 点随机复向量 `idft` 再 `dft` 还原，最大偏差 5.551e-16；CP 前缀与数据段末尾逐点相差小于 1e-12；无多径时两侧都是 0 错、EVM 小于 1e-9；同一个种子跑两遍数字逐位相同。这几条不需要解释，跑 `npm test` 就能看到。

判据是开工前写的，不是做完补的。R9 动手前先交了八条，用户对着改了三处实质内容：延时避开 8 与 16；判据里"无多径误码为零"补上"无噪声、延时与 64 除不尽"这个前提；"至少差两个数量级"删掉，改成等实测再写。这三处改动本身比判据更有信息量——它们说明"验收怎么写"这件事，AI 一个人写不完整：它容易写出自己能过的判据，而有经验的人会先想"这条什么时候会假过"。

OFDM 页在 `docs/images/` 里没有配图（那里只有三张：QAM 一张、卷积码两张），本轮不新截图，PDF 排版时这一节留一页图位，或用线上 `https://240000000.github.io/comm-lab/#/ofdm` 当场打开。

### 1.3 「翻四位还剩几位」：3 和 1 的来回

R10 做任务模式时，能力题要问"12 位比特、翻第 13 到 16 位这四位，硬判决译码后还剩几位错"。这个数要写进题面，于是回仿真里算：关噪声、把四位幅度取反、`decodeHard` 之后逐位比，**只剩 1 位错**。但当时文档里写的是 3 位，而且从 R7 起就一直是 3。

错因不是算错，是跟着旧结论改的。R7 那轮做数字审计，用户指出 preview 里有几处数不实；我在改的时候连这个"还有几位"一起改成了 3，依据是当时脑子里的印象，没有回代码里跑（提交 `34f973e`，tag R7）。数字的来源从"算"变成了"记得"，所以它错得毫无痕迹——没有报错、没有测试变红、页面也没变，只有文档变了。

这两类错误值得分开看。如果是仿真算错，测试会挡住，因为测试断言的是同一个函数；如果是跟着结论改，测试根本管不到文档，只有下一轮真去算一次才会暴露。这也是后来"文档里的数必须先跑一遍"这条规矩的直接来源。

还有一个容易混的地方：开着噪声、2 dB 默认状态下，译码后剩的是 2 位，不是 1 位。两个数都对，取决于是否开噪声。任务模式那道题特意写成"关噪声"，因为只有关噪声时这个数才是确定的、可以在页面上复现的。

题目只翻第 13 到 16 位，不是随手挑的。卷积码页的码字是 28 位（12 位信息加 2 位补零，每输入一位出两位），这四位落在一个约束窗口里，硬判决会把它们错判成同一个方向，译完之后只剩一位残留错误——这个"差一点就全错"的结果比"翻一位全纠回"更能说明纠错能力有上限。翻八位、翻成片片，结果就是纠不回来，也没法学。

改成什么：`docs/preview.md:15` 和 `docs/video-script.md:52` 都改回 1，页面文案本来就是"还有 1 位没纠回来"；提交 `a6192fb`（tag R10）里带着这次改动。

这件事暴露了一个结构问题：同一个事实有三个落点——页面文案、作品介绍、录屏脚本。页面文案跟着代码走，代码改了它会变；后两个是手写的，没人管就会漂。R7 那次只改了文档、没回代码算，漂了三轮才在 R10 被一次"顺便算一下"撞出来。之后的处理是把这类数尽量收到代码里：任务模式的期望值改成由 `numericBer()` 现算，页面读的是同一个函数，文档里写的是这个函数的输出——三处变成两处。

![卷积码页的短序列：原始比特、编码后、加噪后、译码后四行](images/conv-sequence.png)

图里第二行末尾两个虚线格是补零位，第三行的琥珀色格是被噪声打翻的比特，第四行是译码结果。翻四位、译码后仍有一个格子是红的，就是上面说的那 1 位。

### 1.4 「差一个数量级」其实是 2.2 倍

R7 之前，`docs/preview.md` 第六节有一句"两条线在 2 dB 差一个数量级左右"，后面紧跟"就是这个信息差出来的"。用户读到这句停住了：2 dB 硬判决 1.92e-1、软判决 8.72e-2，只差 2.2 倍，不是数量级；用户另外给的 4 dB 一组数（1.52e-1 对 1.45e-2）也和本地复算对不上。

那句话的来路是读图。对数纵轴上，硬判决与软判决两条线在低信噪比处看着隔了将近一个十倍格，就写成了"数量级"。实际复算（种子 20261027、每点 20,000 比特、11 个信噪比点）是：0 dB 2.21 倍、2 dB 6.73 倍、4 dB 18.45 倍（硬 203 对软 11，见 `docs/preview.md:72`）。倍数是随信噪比变的，用一句"差一个数量级"概括它本身就是错的，因为读者会以为整条曲线都差十倍。

| Eb/N0 | 不编码 | 硬判决 | 软判决 | 硬/软 |
| --- | --- | --- | --- | --- |
| 0 dB | 7.90e-2（1,581） | 1.92e-1（3,844） | 8.72e-2（1,743） | 2.21 |
| 2 dB | 3.54e-2（708） | 7.81e-2（1,562） | 1.16e-2（232） | 6.73 |
| 4 dB | 1.26e-2（251） | 1.01e-2（203） | 5.50e-4（11） | 18.45 |
| 6 dB | 2.35e-3（47） | 7.00e-4（14） | 0（0） | — |

表里括号是错误数，分母都是 20,000 比特。这张表是重算出来的，不是从文档里抄的——抄的话就回到 1.3 的老路上去了。

用户另外给的那组 4 dB 数字与本地复算对不上，这件事本身也写进了那一轮的回复：我用本地脚本重算了一遍卷积码三条线，把每个点的错误数与比特总数都打出来，确认 4 dB 是硬 203、软 11。这一处置最终用的是本地可复现的数，而不是任何一个记忆里的数。

改成什么：这句话整段重写成按 4 dB 说，并给出两个具体错误数（203 / 11），不再写倍数形容词。规矩也定了：读图层面的判断不进正文，进正文的数字必须来自代码。同一轮把 `docs/video-script.md:54` 的"软判决明显压过硬判决"换成 2 dB 的 1,562 对 232，让视频里念出来的每一个数都能在页面上复现。

复算的做法也固定下来了：`node` 直接跑 `.ts`（Node 24 自带类型擦除），把 `sweepConv` 的输出打成表，一眼能看出每个点的错误数与分母。这条路径现在写进了 `docs/round-checklist.md` 的收尾清单——每轮结束前，凡是要进文档的数字都从这条路径过一遍，重算不出来就删掉，不留"大概是这么多"。

![卷积码页三条对照曲线：不编码、硬判决、软判决](images/conv-curves.png)

看这张图也能理解为什么"读图"会骗人：两条线在高信噪比处都贴到样本分辨率以下，视觉上间隔被压扁；只有回到数字，才看得出 4 dB 处是 18 倍、2 dB 处只有 6.7 倍。

### 1.5 文案说「能调阶数」，代码写死 16

R6 之前，首页主标题下面那句写的是"打开浏览器就能调 QAM 阶数、噪声强度"，QAM 卡片写"阶数切换、AWGN 噪声注入、EVM 与误符号率实时读数"。实现里 QAM 只是十六点，阶数是常量。用户逐句核对文案时把这处抓了出来，问的是"这句能对上哪一行代码"。

当时有两条路。补功能：动 `buildConstellation`、判决、EVM 口径、曲线扫描，还要改任务模式里"12 dB 只调 16QAM 行不行"那道题的参照，105 条测试得跟着动，前后至少两轮；而当时距 11/18 只剩三周，文档与视频都还是零。改口：只动两行文案和几处文档，几十分钟。

选了改口，提交在 `0170d70`（tag R6）：首页 lede 改成"把信噪比拖大拖小，看 16QAM 的星座点怎么被噪声推离原位"，QAM 卡片改成"16QAM 星座与噪声云、EVM 与误符号率实时读数"；README 与 `docs/preview.md` 都补了"阶数暂时写死 16QAM"。判决理由写在那一轮的存档里，不是事后编的：功能没做完时，"写清楚没做"比"多做一个"更能换来评委会的信任，因为它证明作者知道边界在哪。

补功能那条路具体要动哪些地方，当时也列过：`src/core/qam.ts` 的 `buildConstellation` 已经支持 2/4/16/64，这层不用改；要改的是 `src/core/metrics.ts` 里 EVM 的归一方式、判决的搜索范围、`src/labs/QamPage.tsx` 的三个读数与参数表、`src/core/curve.ts` 的扫描参数，以及任务模式里数值题的期望值。加上测试，至少两轮。这些都不是难事，问题是排在文档与视频前面不划算。

同一个问题在 R10 又出现一次：指令面板要不要假装能换阶数。这次的处理更明确——`src/core/commands.ts:57` 直接回"这个页现在固定 16QAM，阶数切换还没做——不是没听见，是这一版确实没这个功能"，并且有一条测试断言阶数输入不改任何参数。假动作（回一句"已切换到 64QAM"但什么也没发生）会让评委以为整页都在演，明确拒绝反倒成了"边界说得清楚"的例证。

## 第二章 架构设计

六个决定，每个说清楚为什么不是另一个选择。目录结构在 README 里，这里不重复。

### 2.1 纯前端，没有后端

比赛规则要求运行时不调任何模型 API，评委也没有 key；这一条直接把"云端算、前端看图"的路线排除了。剩下的选择是要不要一个本地 Node 服务给前端供数据：那样能跑更大的样本，但要多一步启动、多一个端口、多一处会坏的地方，GitHub Pages 也放不下。

纯前端换来的是打开即用：静态文件、无账号、无网络请求；代价是浏览器里只有单线程 JavaScript，长时间批量仿真做不了，数据也存不住，分享只能靠 URL。四页之间的跳转因此手写 hash 路由（`src/router.ts`），`location.hash` 加 `hashchange`，十几行，没有引 react-router，也没有用 History API——静态托管下刷新会 404。

这条约束还留下过一个已知缺口：到 R23 为止，CI 只跑 build 与 Pages 部署，没有跑测试。测试靠本地 `npm test`，提交前自觉跑。R24 把这一步补上了：workflow 现在依次跑 `npm ci`、`npm test`、`npm run check:docs`、`npm run build`，任何一步失败都不上传产物；Node 版本也从 22 提到 24，与本机验证过的 v24.18.0 同一条线，免得在 Actions 上踩 `node --test` 跑 `.ts` 的版本差异。写在这里是为了让读者知道——R23 之前，"CI 绿"确实不等于"测试绿"。

### 2.2 core 与 labs 分层

`src/core/*` 只放纯函数：不碰 DOM、不读 `window`、不认识 React。`src/labs/*` 只做渲染与交互：canvas 画图、滑块、状态。中间用普通函数调用，没有全局 store，也没有 Context。

这样分的直接收益是测试：node 自带 runner 可以直接 `import` core 里的函数，不需要 jsdom、不需要渲染组件。现有 core 文件是 `qam.ts`（星座映射）、`rng.ts`（随机数）、`channel.ts`（加噪与判决）、`metrics.ts`（统计口径）、`ber.ts`（理论曲线）、`curve.ts`（扫描）、`conv.ts`（卷积码与两套译码）、`dft.ts`（按定义的变换）、`ofdm.ts`（两径链路）、`missions.ts`（任务模式）、`commands.ts`（指令解析）。

分层的证据可以自己验：`grep -rn "^import .*from '" src/core/*.ts | grep -v "from '\./"` 的输出为空，也就是 core 里没有一条非相对路径的 import，既没有引第三方库，也没有 import React。界面改动不会碰到算法，算法改动会立刻让测试变红。

一次典型的数据流可以说明边界在哪：QAM 页把 `snrDb` 与 `seed` 两个数交给 `simulateAwgn`，后者返回 `Stats`（含点位、判决、错误计数、EVM）；页面拿到的是一摞普通对象，画进 canvas，再算出三个读数的字符串。这条链上没有订阅、没有副作用、没有全局状态，所以同一次输入必然得到同一屏画面。四页都是这个形状，区别只在 `Stats` 的字段多少。

一个具体的坑：Node 的 ESM 不做扩展名补全，core 内部互相引用必须写 `./qam.ts` 而不是 `./qam`，否则 `node --test` 直接报 `ERR_MODULE_NOT_FOUND`。这些 import 现在全部带扩展名。

分层不是绝对的。R10 把指令面板挂到了 QAM 页，需要拿到那一页的 `setSnrDb`，所以 `src/labs/QamPage.tsx` 里插了一行组件与三个回调。这是对"只允许 App 与路由接第四张卡"的一次越界，当时在回复里单独交代过，用户确认允许。这一处写在报告里，是因为过程记录不能只记守规矩的部分。

core 分成 11 个文件而不是一个大文件，理由同样是可核对：每个文件对应一个能在教材上找到的概念（星座映射、随机数、加噪与判决、统计口径、理论曲线、扫描、卷积码、变换、OFDM 链路、任务模式、指令解析）。写报告时要指"哪一行的常数"，文件名本身就是坐标；如果全塞进 `core.ts`，同样的引用会变成"大概三百行那里"。代价是 import 路径变长，以及必须写清 `.ts` 扩展名。

### 2.3 测试用 node 自带的 runner

这台机器装依赖出过问题，vitest 一次要拉一百多个包；项目本身又是零测试依赖的。Node 24 默认开启类型擦除，`node --test` 能直接跑 `.ts`，所以 `package.json` 里只有一行 `"test": "node --test"`，测试放 `tests/*.test.ts`，15 个文件、`npm test` 报 171 条，本机热跑 `duration_ms` 948.4，干净克隆里墙钟 1.58 s。

代价说清楚：没有快照测试、没有覆盖率报告、没有并发隔离，断言只有 `node:assert`；测试文件里的 import 也必须带 `.ts` 扩展名；`grep -c "^test("` 数出来的行数会比实际用例少，因为子测试与循环生成的用例不在顶层。换来的是 `npm ci` 只装 28 个包（`package-lock.json` 里 90 条 `node_modules/` 记录，其余 62 条是 oxlint、rollup、esbuild 各平台的二进制，npm 只取当前平台那一个），整条依赖树小到可以一眼看完。

配置也几乎没有：没有 `vitest.config.ts` 一类的东西，`node --test` 自己找 `tests/` 下的 `*.test.ts`。这条不是想当然——R1 那轮先用临时目录探过一遍，确认 Node 24 能发现 `.ts` 测试并执行，才把 `"test": "node --test"` 写进 `package.json`；探针跑出来 1 条用例通过，退出码 0。

测试里最值钱的是两类。一类钉可复现性：同种子两次逐位相同（`tests/metrics.test.ts:10`、`tests/ofdm.test.ts:50`）。另一类钉口径：任务模式的期望值必须等于现算值（`tests/missions.test.ts` 里那条断言），防止有人手抄一个数进去。第三类是边界：5/5 与 0/5 各一条，容差贴边四条（0.91、0.89、1.09、1.11）。

四档的数值也不再靠手抄。页面默认按 20,000 比特取样本（64QAM 每符号 6 比特，向上取整成 3,334 个符号、20,004 个比特），12 dB、种子 20261027 下，`npm run check:docs` 每次提交前重算这张表：

| 阶数 | 符号数 | 比特数 | 实测错比特 | 实测 BER | 理论 BER | EVM |
| --- | --- | --- | --- | --- | --- | --- |
| BPSK | 20,000 | 20,000 | 0 | 0 | 9.01e-9 | 25.18% |
| QPSK | 10,000 | 20,000 | 0 | 0 | 3.43e-5 | 25.19% |
| 16QAM | 5,000 | 20,000 | 610 | 3.05e-2 | 2.81e-2 | 25.33% |
| 64QAM | 3,334 | 20,004 | 2,313 | 1.16e-1 | 1.12e-1 | 25.35% |

BPSK 与 QPSK 的零不是真没有错：理论值 9.0e-9 与 3.4e-5 都低于这批样本的分辨率 1/20,000，跑不出错才是正常。

### 2.4 DFT 按定义做 O(N²)

64 点子载波，一个符号的变换是 64×64 = 4096 次复数乘加；一次完整链路（200 个符号、两路信道、判决、统计）实测 8.6–15.4 ms，拖滑块不卡（`docs/dialogues/2026-10-26-session-02.md` R9 节的实测段，2026-10-31 复测同量级）。

没有上 FFT，理由不是不会写，而是收益不划算：64 点尺度上 FFT 只省毫秒，却要处理位反转、旋转因子表、非 2 的幂的退化分支，出错面比省下来的时间值钱。按定义算，一个符号 4096 次复数乘加，200 个符号大约几百万次浮点运算，浏览器里就是十几毫秒的量级；换成 FFT 能把这个数压低一个量级，但一次拖滑块的预算本来就只有一帧的时间，省下来的那部分用户感觉不到。`src/core/dft.ts:39` 就是三重循环的定义式，连同 `idft`（`src/core/dft.ts:68`）一共 94 行，逐项可对照教材。用户当时的原话是"先按定义算的最笨版本跑通，换快速算法前必须说一声"，这条被当成约定写进了那一轮的存档。

写这个函数时踩过一个更基础的坑：第一版把 IFFT 出来的复数时域只取实部送进信道，收端再对纯实数做 DFT，结果频域相邻子载波互相混叠，连 delay 0 都出现 44% 的误符号率。改成全程复基带之后，delay 0 立刻变成 0 错。这件事说明"按定义写"并不自动等于"物理对"，复基带这件事必须在文档里说清楚。

### 2.5 指令面板只做四条

面板是"意图控制"的展示件，不是产品功能。做成四条：噪声调大、噪声调小、重跑、重置。理由一致——它们都能在本地立即执行、都能写测试、都不需要理解自然语言。

识别用正则，优先级固定为：空串、阶数、重置、重跑、调大、调小、认不出（`src/core/commands.ts`）。噪声一律夹在 0–20，19 dB 再说"调大"得到 20 而不是 21，`Math.min(20, Math.max(0, Math.round(v)))` 一行搞定。阶数的输入被单独拦下来，回一句明确的话，不动任何参数。面板标题旁写着"本地规则解析，不联网、不调模型"，这句话在评审口径里比功能数量更值钱。

五种典型输入与实际回复（全部出自 `parseCommand`，`tests/commands.test.ts` 里有断言）：

| 输入 | action | 回复 |
| --- | --- | --- |
| 噪声调大 | `snr-up` | 信噪比 12 → 13 dB，噪声小了一点。 |
| 噪声调大（已在 20 dB） | `snr-up` | 已经是上限 20 dB，再往上没有意义了。 |
| 噪声调小（已在 0 dB） | `snr-down` | 已经到底 0 dB，再往下就不是噪声大小的问题了。 |
| 换成 64QAM | `reject` | 这个页现在固定 16QAM，阶数切换还没做——不是没听见，是这一版确实没这个功能。 |
| 今天天气怎么样 | `reject` | 只听懂四条：噪声调大、噪声调小、重跑、重置。 |

第四条是这块面板存在的意义：被拒绝时它说清"没这个功能"，而不是假装执行了。返回值里的 `snrDb` 永远是 0 到 20 的整数，无效输入不会抛异常，也不会改状态——这两条都在测试里固定住了。

还有一点没做：没有分词、没有同义词表、没有容错距离。"噪声给大一点"这种话它认不出，会回"只听懂四条"。这是有意的取舍——加一层模糊匹配，就要为"匹配错了但看起来对"负责，而这一页要演示的恰好是"边界清楚"。

不做自然语言理解，也是同一个取舍：这一版没有模型可调，做一个"看起来懂"的假解析，等于把不确定性引进来。正则能覆盖的输入就那些，覆盖不到的老实说没听懂。

### 2.6 EVM 按子载波各自归一，这一条偏离教材

教材里 EVM 通常用单一复增益归一：先估一个 g，再用 `mean|r - g·s|²` 的相对值。最初也这么写，结果 cpLen 16、delay 9（完全在 CP 内、理论上没有码间干扰）时，EVM 显示 50%，和事实对不上。

原因是两径信道本身是频率选择性的：`H[k] = 1 + 0.5·e^(-j2πk·9/64)`，每个子载波的增益不同，单一 g 消不掉这种逐载波起伏，残余被算进了 EVM。改成每个子载波用自己的那串点拟合 g_k，再算该载波的均方根误差：delay 9 的有 CP 侧立刻变成 0.0%，无 CP 侧 22.86%（2026-10-31 用同一套函数复算）。

这个口径要明说清楚，因为它和教材不是一回事：它衡量的是"去掉每个子载波自身增益之后点有多散"，不是"相对理想位置的绝对误差"。在频率选择性信道里，后者会被信道本身放大，看起来像解调坏了，其实没有。页面上的参数表与 `docs/preview.md` 都写了这条口径，没有藏。

每个子载波的增益是这么估的：把该子载波上 200 个符号的理想值记为 s，接收值记为 r，取使 `Σ|r - g·s|²` 最小的 g，也就是 `g = Σr·conj(s) / Σ|s|²`，再算 `EVM_k = sqrt(mean|r - g·s|² / |g|²)`。这是最小二乘，不是物理信道估计——它把"信道增益"和"残余误差"分开，只留后者。区别在于：真正的信道估计要用导频，这里没有导频，也不需要估计信道，只是为了让 EVM 这个读数有意义。

副作用也要说：因为 EVM 已经把每载波增益除掉，它不能用来判断"信道把信号衰减了多少"。任务模式里那道"12 dB 只调 16QAM 能不能压到 1e-4"用的是 BER 而不是 EVM，就是为了避开这个容易误读的量。

2026-10-31 实测，Windows 11、Node v24.18.0、npm 11.16.0、家宽直连、全新目录：

| --- | --- | --- |

`npm run dev` 起在终端打印的地址（本机是 `http://localhost:5183/`），打开后进 `#/qam`，看到的就是第一张图：16QAM 的 16 个点、旁边的 4 位格雷码标签、默认 12 dB 的琥珀色点云，下面三个读数和一条 0–20 dB 的误码率曲线。

三个数有前提：`npm ci` 的耗时第二次会明显变短（首次 2.6 s 左右，缓存后 1.95 s）；杀毒软件正在扫描时 build 会翻倍；机器不同、网络不同，这几个数都会变，能复现的是"秒级"，不是小数点后两位。

如果四步里任何一步失败，README 的常见问题表列了三种：`npm ci` 失败先删 `node_modules` 改用 `npm install`；页面空白先看控制台，通常是 Node 低于 24；只有线上 404 是 `base` 路径问题，本地不会复现。

不开浏览器也能验一半：`npm test` 会告诉你 171 条过没过；`npm run build` 会告诉你产物有多大（本轮 `dist/assets/index-*.js` 约 314 kB、`index-*.css` 约 27 kB，哈希随内容变）。剩下的一半只能打开看——点云、曲线、标签位置这些没有断言。

### 3.2 Node 版本与零新增依赖

`node -v` 必须是 v24 及以上。理由是测试直接跑 `.ts`：Node 22.6 需要显式开类型擦除，24 默认开启，`node --test` 才能 import `tests/` 里的 TypeScript 文件。低于 24 的表现是测试文件语法错误，不是用例失败，README 的常见问题表里写了这一条。

零新增依赖的验证方法有三步，都可以当场跑：

1. `cat package.json`：`dependencies` 里只有 `react` 与 `react-dom`；`devDependencies` 里只有 vite、typescript、oxlint、`@vitejs/plugin-react` 和三个 `@types`。
2. `grep -c '"node_modules/' package-lock.json` 输出 90：当前平台实际装 28 个，其余 62 条是 oxlint、rollup、esbuild 各平台的二进制，npm 按平台取一个。
3. `grep -rn "^import .*from '" src/core/*.ts | grep -v "from '\./"` 输出为空，core 里没有引任何第三方库。

没有通信库、没有数值库、没有绘图库——星座图、曲线、时域波形都是 canvas 手画，FFT、Viterbi、QAM 映射都在 `src/core/` 里手写。这一条不是自证，上面三条命令就是证据。

代码检查用的是 oxlint，一个 Rust 写的 linter，体积小、不需要再装一堆 ESLint 插件，`npm run lint` 报的是"0 warnings and 0 errors"（扫描文件数随源码增删变，不写死）。它不是测试的替代品，只保证没有未使用变量、没有明显写错的地方；真正的逻辑靠 171 条测试。

"运行时不调模型、不联网"也能当场验：打开开发者工具的 Network 面板，四页各点一遍，除了本地静态文件没有任何请求；`src/` 里搜不到 `fetch`、`XMLHttpRequest`、`WebSocket`，也没有任何 base URL 常量。这一条比说"纯前端"有用，因为它是可观察的行为，不是架构描述。

### 3.3 种子为什么定死

随机数用 mulberry32 生成均匀分布，Box–Muller 转成高斯噪声。界面上显示的不是用户输入的那个种子，而是派生后的：`deriveSeed(seed, snrDb)`（`src/core/metrics.ts:51`）把信噪比揉进种子，所以同一个种子在不同信噪比下得到不同的噪声序列，同一组参数下重跑则逐位相同。默认种子 20261027，四个实验台共用（`src/labs/QamPage.tsx:38`、`src/labs/ConvPage.tsx:27`、`src/labs/OfdmPage.tsx:12`、`src/core/missions.ts:46`）。

"同一个种子跑两遍数字一样"不是承诺，是测试：`tests/metrics.test.ts:10`（同种子同信噪比，跑两次每一个统计量逐位相同）、`tests/ofdm.test.ts:50`（同一个种子跑两遍数字逐位相同，换种子会变）。任务模式的五道题期望值也是每次现算（`src/core/missions.ts:61` 的 `numericBer()` 直接调 `simulateAwgn`，测试再断言页面判分用的数等于现算结果）。

为什么值得定死：读图的人看到的点云位置、读数的小数位、曲线的每个点，都依赖于同一条噪声序列。种子随机的话，同一句话在两次打开时会对不上，任何"看这里是不是 2.9e-2"的复核都会失效。

界面上同时显示两个数：输入框里的 20261027，以及下面一行"本次实际用的种子是 1,883,523,065（由种子与信噪比共同派生）"。前者是给人对的，后者是给复核用的——把输入框改回去、信噪比也改回去，派生值必然回到同一个数；只要这个数变了，就说明参数没对上，不用去猜读数为什么不一样。这个设计来自一次具体的困惑：早期只有输入框，改了信噪比再改回来，读数对不上，还以为是 bug。

### 3.4 三条原理短片

三个实验台上各有一个按钮，点开在页面里放一段几十秒的片子，不跳走。这个要求的原话在 `docs/dialogues/2026-10-28-session-03.md:316`：「三个实验台上面我做了三条原理短片……想让用户点开就能在页面里看，别跳走——跳走了就不像这个工具的一部分了。」片子不是录屏，是按实验台的参数算出来的点与读数，逐帧画成 960×540。

文件、时长与体积如下。时长不是从文件名或按钮上抄的，是用 Node 读 MP4 的 `mvhd`，timescale 与 duration 相除：

| 文件 | 时长 | 视频字节 | 海报字节 |
| --- | --- | --- | --- |
| `public/shorts/qam-16qam.mp4` | 42.000 秒 | 1,697,865 | 14,738 |
| `public/shorts/conv-viterbi.mp4` | 48.000 秒 | 435,941 | 17,564 |
| `public/shorts/ofdm-cp.mp4` | 59.000 秒 | 1,004,666 | 43,697 |

三条合计 3,138,472 字节，约 3.0 MB；最大的一条 1.7 MB，在 R20 降码率之前，QAM 那条是 6.6 MB。

同源有三条证据，都能当场查：

种子。QAM 海报底部印着「种子 20261027 · 同一个种子，每个信噪比重新抽样」，和页面输入框的默认值、`src/core/metrics.ts` 的 `deriveSeed(seed, snrDb)` 是同一条链。

读数。把 QAM 短片 seek 到 27 秒截一帧，0 dB 那一屏写的是 BER `2.86e-01`、`22,916 / 80,000 比特`，SER `7.41e-01`、`14,811 / 20,000 符号`。这组数与 `simulateAwgn({ order: 16, snrDb: 0, symbolCount: 20000, seed: 20261027 })` 的输出逐位相同，也是 `docs/preview.md:29` 与 `npm run check:docs` 钉住的那组；同一支片子在 8.2 dB 写 `7.71e-02`、`6,168 / 80,000`，在 16.4 dB 写 `4.9e-04`、`39 / 80,000`，都能用同一条链路重算。

参数。OFDM 海报写「一个 OFDM 符号（80 个采样）」「CP 16」「数据段 64」「64 个子载波上的接收点」，对应 `src/core/ofdm.ts` 的 `SUBCARRIERS = 64` 与页面默认 `cpLen = 16`（64 + 16 = 80 个采样）。卷积那条是 11 个比特的小样本，画面里写「2 个错全纠回来了：自由距离 5 的码，最多能纠 2 位」，与 `freeDistance()` 返回 5、`correctionCapability(5)` 返回 2 一致。

页面里怎么挂：三个页面各一行 `<ShortFilm file="…" poster="…" seconds={…} />`（`src/labs/QamPage.tsx:92`、`src/labs/ConvPage.tsx:160`、`src/labs/OfdmPage.tsx:69`），秒数分别是 42、48、59。组件只收这三个 props，路径由 `shortFilmUrl(BASE_URL, file)` 拼，build 时自动带 `/comm-lab/` 前缀；加载失败显示「短片还没放上来，稍后再试」，不会留一个空白框。`tests/shortFilm.test.ts` 钉住三件事：根路径与 `/comm-lab/` 两种 base 都能拼对、不会拼出双斜杠、59 秒不会被取整成 1 分。

和「可复现」的关系：短片是仓库里的静态文件，字节数固定，`git show R20c:public/shorts/ofdm-cp.mp4 | wc -c` 就是 1,004,666，不下载整包也能核；秒数能从容器里读；画面里的数字又能回到 `src/core` 重算。三层各自可查，不靠「我记得当时是这么写的」。

### 3.6 换一台机器可能不一样的地方

换行符。工作区按 LF 写，Git 在 Windows 上会提示"LF 将被替换为 CRLF"，不影响运行，但 `git diff` 里可能看到整文件的换行属性变化。macOS 与 Linux 没有这层提示。

监听地址。Vite 默认只监听 `[::1]`，本机 `curl http://127.0.0.1:端口` 会失败，`http://localhost:端口` 才能通。这跟代码无关，是 IPv6 优先的默认行为；报告里所有本地地址都用 `localhost`。

耗时。`npm ci` 有缓存与无缓存差一倍；build 与 test 受杀毒软件实时扫描影响；机器核数不同，`npm test` 的并发度也不同。能复现的是量级，不是小数。

`npm test` 的并发也值得说一句：`node --test` 默认按 CPU 核数并行跑测试文件，而本项目每个文件都自己造随机数、不共享状态，所以并行不会让结果变化。如果哪天有人加了跨文件共享的可变状态，它会先变成偶发失败，而不是稳定失败——这类问题的排查成本很高，所以测试文件一律不互相 import。

如果 `npm ci` 报 lockfile 不一致（换过 Node 大版本时偶发），README 的处理是删掉 `node_modules` 改用 `npm install` 重新生成 lockfile；这条路会偏离"锁定版本"的前提，所以只作为救急方案，不写进复现步骤。

截图。无头浏览器加 `--force-device-scale-factor=2` 得到的 1800×1800 图是模拟高分屏，真实设备的 devicePixelRatio 由显示器决定，`dpr` 上限在代码里钳到 3。

字体。canvas 里用的是 Consolas 与 `Cascadia Mono`，Linux 上没有这两个字体，会退回等宽字体，标签宽度略变，字号与位置不变。

发布路径。`vite.config.ts` 在 build 时把 `base` 设成 `/comm-lab/`，本地 dev 是根路径。把仓库改名或换组织后，这个值要跟着改，否则线上白屏。

浏览器。canvas 的 `measureText`、`setLineDash`、`devicePixelRatio` 在 Chromium 与 Safari 上行为一致的部分才被用到；没测过 Firefox 与旧版 Safari，标签底色块的位置依赖 `measureText` 的结果，理论上会差一两个像素。
